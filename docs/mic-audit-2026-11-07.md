# Microphone implementation audit — 2026-11-07

Triple-check of the Watcher mic capture path (PTT + wake word share it)
against every available reference, per John's request. Conclusion first,
then the evidence.

## Conclusion

**The implementation matches all references.** Chip selection, I2C
addressing, open parameters, channel mask, gain mechanism, I2S slot
configuration, read contract, AFE configuration, and every ES7243E
register write in the vendor driver decode correctly against the
datasheet. No code divergence explains "transient at take start, then
digital silence."

What remains untested is the **live register state of the chip on the
device** — everything above is correct *by construction*. The decisive
next instrument is a register dump from the running device (intended
state table below), taken (a) while wake-word listening, (b) during a
PTT take, (c) right after a take.

## Verified matching (with the trap each one hides)

1. **Codec chip**: ES7243 @0x13 / ES7243E @0x14, runtime I2C probe —
   BSP identical (sensecap-watcher.c:1038-1072; ours ptt.c:177-210).
2. **Wiring (schematic)**: mic → ES7243E AINR (nets ADC_MIC1P/N),
   ES8311 DAC loopback → AINL. Mic is therefore the RIGHT I2S slot;
   BSP RX slot_mask = SLOT_RIGHT (sensecap-watcher.c:940). Ours opens
   channel=2 + mask(1) exactly like `bsp_codec_set_fs` (:1120-1126).
3. **Gain mechanism**: driver `es7243e_adc_enable()` rewrites PGA
   regs 0x20/0x21 to 0x10 (0 dB) at every enable, clobbering open's
   0x1A (+30 dB). Gain survives anyway: `esp_codec_dev_set_in_gain`
   stashes `mic_gain` on the dev and `esp_codec_dev_open` re-applies
   it via `_update_codec_setting` after enable (esp_codec_dev.c:125,
   :215). Verified in both the BSP's reused-dev flow and our
   per-acquire dev flow. 27.0 dB → reg 0x19 (0x10 | 27/3).
4. **PGA input select**: datasheet 0x20/0x21 bit4 = SELMIC1/SELMIC2.
   Driver sets bit4 in open (0x1A), enable (0x10), and set_gain
   (0x10|steps) — inputs are never deselected.
5. **Digital volume**: 0x0E = ADC_VOLUME; power-on default 0x00 is
   **−95.5 dB**. Driver open writes 0xBF (0 dB). If this write were
   ever skipped the chip would be digitally muted; our flow runs
   open at codec_new and nothing else writes 0x0E.
6. **Mutes**: SDP_OUT_MUTE (0x0B bits7:6, default = mute both) —
   driver open writes 0x0B=0x00 (unmute); `set_in_mute(false)` via
   `_update_codec_setting` keeps it unmuted. ADC automute (0x0F
   bits5:4) — driver writes 0x0F=0x80 → automute disabled, ALC off,
   dynamic HPF on. ALC off (0x0F bit6=0).
7. **Analog power**: 0x16 power-down bits — enable writes 0x3F
   (modulator resets) then 0x00 (all blocks on). 0x17 VMIDSEL —
   open=2 (normal), enable=1 (speed charge). 0x00 CSM_ON + reset
   pulse 0x1E mid-sequence. 0x01=0x3A = MCLK/BCLK/CLKADC/ANACLK on.
   0x03 ADC_OSR=0x20 (128×fs), consistent with 0x0D ADC_SCALE=0 dB
   recommendation. 0x09/0x0A S1/S3 power-up state timers: Espressif
   tuning, shared by BSP and us.
8. **I2S**: BSP slot macro == ours (16-bit, AUTO slot width,
   SLOT_BOTH pre-config, ws=16, bit_shift, left_align). Clocks:
   codec dividers assume MCLK=256fs; our STD clock default matches.
9. **Reads**: factory feed/record tasks read exactly like ours
   (esp_codec_dev_read of chunksize×1 int16 through the masked open;
   DRV_AUDIO_I2S_CHANNEL=1). BSP's software `<<gain` shift defaults
   to 0 (Kconfig) and its feed `<<2` is commented out — no hidden
   factory gain stage.
10. **AFE**: factory (AFE_CONFIG_DEFAULT era): aec off, total_ch=1,
    mic=1, ref=0, MORE_PSRAM. Ours (afe_config_init "M", SR,
    LOW_COST): same channel geometry; se/ns/agc/vad on,
    DET_MODE_90. Processing-block differences affect WakeNet only —
    PTT takes are raw codec reads and are equally silent.

## Real divergences (none sufficient alone; ranked)

D1. **Codec power cycling.** The factory opens the codec once at
    boot and, with VI_SR enabled, *never closes it* — streaming is
    continuous. We fully power the codec down/up on every acquire/
    release (every take, every wake-word suspend/resume): 0x16←0xFF,
    VMID discharge, clocks off, then the full S1/S3 sequenced
    power-up. This explains the ~100 ms transient at each take start.
    It does not by itself explain silence for the remaining seconds —
    unless a power-up lands in a bad state intermittently (some takes
    *do* catch loud events; the wake feed's idle floor differs from
    the takes' floor).

D2. **First enable runs without MCLK.** BSP starts I2S (MCLK
    running) *before* `es7243e_codec_new()` executes the register
    init + internal `adc_enable`. Our `codec_probe()` runs at
    ptt_init with no I2S channel in existence, and the first real
    acquire's `esp_codec_dev_open` skips `codec->enable` (the
    driver's `enabled` flag is already true from codec_new), so the
    chip's first power-up sequence ran clock-less. Later cycles do
    run enable with clocks (close clears the flag). Unproven as a
    cause; the register dump + a keep-open experiment settle it.

D3. **I2S channel defaults.** BSP sets chan_cfg.auto_clear=true and
    intr_priority=4; we use I2S_CHANNEL_DEFAULT_CONFIG. Hygiene, not
    signal path.

D4. **AFE generation gap** (see 10 above). Wake-word only.

## Intended live register state (for the dump)

While listening or recording, the ES7243E should read:
0x00=0x80, 0x01=0x3A, 0x03=0x20, 0x09=0xCA, 0x0A=0x85, 0x0B=0x00,
0x0D=0x00, 0x0E=0xBF, 0x0F=0x80, 0x14=0x0C, 0x15=0x0C, 0x16=0x00,
0x17=0x01, 0x20=0x19, 0x21=0x19, 0xFC bit0 (FLAG_ADCAM)=0,
0xFD=0x7A, 0xFE=0x43 (chip ID — proves I2C reads hit the real chip).

## Addendum (2026-11-07, during the 0.4.41 build)

- `es7243e_get_reg()` in the vendored esp_codec_dev is broken
  upstream: it passes `&value` where `value` is already `int*`, so
  the read byte overwrites the low byte of the local pointer and the
  caller's int is never written. 0.4.41's dump therefore reads via
  the control interface (`codec_ctrl_->read_reg`) directly.
- Unrelated sighting the same morning: fw 0.4.40 panicked once at
  uptime ~1164 s — Guru Meditation, interrupt WDT on CPU0, backtrace
  inside the legacy I2C driver's ISR with `i2c_hw_fsm_reset` on the
  stack (ELF 93211813a, symbolized). The I2C bus (codec ctrl,
  PCA9535, touch) wedged and the driver's ISR recovery spun past
  the IWDT. Single occurrence; device recovered cleanly. Watch for
  recurrence.

## Loopback results (2026-11-08, fw 0.4.42.1)

Phase 0 (baseline): L rms 6 (dead), R rms 61 (settle tail).
Phase 1 (ES8311 opened, no tone): L rms 1909 broadband (DAC idle on
the loopback input), **R rms 9 — mic stayed at digital floor with
the ES8311 powered**, weakening the pure ADCVREF-starvation story
(caveats: ADCVREF may sit in the ES8311's ADC power domain, not
energized by a DAC-only open; settle was 400 ms).
Phase 2 (1 kHz tone, amplitude 12000, vol 80): L Goertzel 9165 —
**the DAC→AINL→ADC→I2S chain is proven good with a real analog
signal**. R also carried the tone near full scale (pk 32712,
Goertzel 8572). John confirmed he HEARD the tone — our firmware
raises CODEC_PA at boot (eyes.c expander power-up), so an acoustic
route exists; electrical/internal coupling not yet excluded.
Pending discriminator: loopback re-run while John shouts/taps —
which phases hear it splits power vs sensitivity vs dead element.
(0.4.42's first run stopped at phase 1: es8311 open ESP_ERR_NO_MEM
— TX DMA vs ~12 KB free internal RAM; fixed in 0.4.42.1 with
dma_desc_num=3/frame=128, PSRAM measure buffer, transient skip.)

## Result (2026-11-07, fw 0.4.41)

Live dump while wake-word listening: **every register 0x00–0x21
matches the intended table exactly** (00:80, 01:3a, 03:20, 09:ca,
0a:85, 0b:00, 0d:00, 0e:bf, 0f:80, 14:0c, 15:0c, 16:00, 17:01,
18:26, 19:77, 1a:f4, 1b:66, 1c:44, 1f:0c, 20:19, 21:19). The
reply's tail (0xF9/0xFC/0xFD/0xFE + acquired flag) was clipped by
the console telemetry mirror's line handling; immaterial — automute
is disabled at its enable bits (0x0F), and readbacks this exact
could not come from a mis-addressed chip.

**The digital path is exonerated by direct measurement**: codec
state correct, reads error-free at real-time rate, yet airborne
speech never becomes samples while transients and occasional loud
events do. Remaining suspects are analog: mic element/bias, the
AINR coupling, the acoustic port — or an interaction between our
per-take codec power-cycling and this unit's analog state (VMID /
bias charge that collapses ~100 ms after power-up would produce
exactly the observed take envelope). Deciding experiments: (1) the
tap test during a take; (2) a factory-style keep-open build that
never power-cycles the codec.

## Schematic smoking gun (2026-11-07, post-audit)

Reading the production PDF (sheet 8, DNP marks): mic U11 VDD is fed
by R160 (populated) from net **ADCVREF**; the ADC_3V3 option (R155)
is DNP. ADCVREF is pin 15 of U14 (ES8311) — that chip's internal
ADC reference output (C95/C98 1uF decoupling; drives nothing else).
The ES8311's analog/reference section is powered only by driver
register writes on open (SYSTEM_REG0E et al). **Our firmware has
never initialized the ES8311** (no playback path exists), while the
factory firmware and XiaoZhi create the speaker codec at startup.
Conclusion: the mic element has had no supply in every test;
an unpowered MEMS output + floating AINR explains the constant -1
DC baseline, the bit-identical per-take transient, and the stray
EMI "loud events". Remaining wiring verified sane: OUTPUT->R93->
ADC_MIC1P->R108 10K->C86 1uF->AINRP; MIC1N grounded via R90/R94
(pseudo-differential); ES8311 MIC1P/N caps C93/C94 DNP (its ADC
unused). fw 0.4.42 tests it in phases: baseline record, ES8311
init only, then 1 kHz loopback tone.
