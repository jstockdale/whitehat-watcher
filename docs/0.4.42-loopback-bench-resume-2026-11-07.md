## Why this test is decisive (one-paragraph recap)

The mic-audit (`docs/mic-audit-2026-11-07.md`, "Schematic smoking gun")
found mic U11's VDD is fed via populated R160 from **ADCVREF** — pin 15
of the ES8311 (U14), its internal reference output; the ADC_3V3 option
R155 is DNP. Our firmware never initializes the ES8311 (no playback
path), while factory/XiaoZhi create the speaker codec at startup. That
explains every observation since September: constant −1 DC baseline,
sample-identical per-take transients, stray EMI peaks on a floating
input. 0.4.42 tests it directly instead of arguing from the schematic.

**Important expectation-setter:** on 0.4.42 the test *closes* the ES8311
again at the end (`esp_codec_dev_close(lb_dac_dev_)` in
`ptt_loopback_test`). So even a perfect phase-1 result does **not** leave
the mic powered — a PTT take taken right after the test on 0.4.42 is
expected to be silent again. Do not re-run PTT on 0.4.42 as a
confirmation; the confirmation is a take on the fix build.

## The likely fix build (0.4.43) — outline, not built

If phase 1 lights up, the permanent fix is small and the loopback code
already contains it: `lb_es8311_open()` in ptt.c creates the ES8311 DAC
device exactly as the BSP does (I2S0 TX channel, GPIO16 dout, ES8311 at
its default I2C address, `use_mclk=true`, out vol 80). The fix:

- Promote that creation/open from the diagnostic to a real init path:
  create + open the ES8311 **once** (at boot after I2S exists, or on
  first mic acquire) and **keep it open** — factory-style — instead of
  closing it after the test.
- Keep `dbg loopback` in the build for one verification cycle (phase 0
  of a rerun then doubles as a regression check; note its phase 0/1
  distinction collapses once the ES8311 is already open, so the real
  verification on 0.4.43 is an ordinary PTT take + a "Hey Muse"
  wake-word attempt).
- Open questions for John when building it, not blockers for the test:
  keep-open permanently vs. close on sleep (the device has a real
  power-off path via EXP_POWER_ON/OFF); whether speaker playback
  (future TTS) should share this same device handle from day one
  (it should — one owner, like the mic handoff rule).
