## Background

Regression diff (2026-09-27): camera code is byte-identical between working v0.3.11 (last good snapshots 2026-09-25 02:37) and broken v0.4.0. What v0.4.0 added was internal-RAM pressure (seal/mbedTLS/WIA1 tasks). Failure chain:

1. A transient SPI failure occurs — most plausibly `ESP_ERR_NO_MEM` on the 4 KB `MALLOC_CAP_DMA` bounce buffer the IDF SPI driver allocates **per transaction** whenever the RX destination lives in PSRAM (errno was unlogged, hence unconfirmed).
2. `sscma_client_ops.c` ignored the `sscma_client_read()` return value and advanced `rx_buffer.pos` over stale bytes anyway.
3. Parser desyncs permanently → "rx buffer is full" → camera stays dead even after SPI recovers.

A paperclip hard-power-cut may fix a wedged unit once (clean heap), but the fragility stays until these firmware fixes land.

## What was built

**1. Failed-read handling (`sscma_client_ops.c`)** — the parser loop now checks the `sscma_client_read()` return. On failure: log `esp_err_to_name()`, back off 25 ms, flush the partial frame (`rx_buffer.pos = 0`), and continue — the position is no longer advanced over stale bytes.

```c
esp_err_t rret = sscma_client_read(client, client->rx_buffer.data + client->rx_buffer.pos, rlen);
if (rret != ESP_OK)
{
    ESP_LOGW(TAG, "sscma_client_read failed: %s; flushing %u partial byte(s)", ...);
    vTaskDelay(pdMS_TO_TICKS(25));
    client->rx_buffer.pos = 0;
    continue;
}
client->rx_buffer.pos += rlen;
```

**2. Persistent internal DMA staging buffer (`sscma_client_io_spi.c`)** — allocated once at SPI IO init via `heap_caps_malloc(max_trans_bytes, MALLOC_CAP_DMA | MALLOC_CAP_INTERNAL)` (max transaction size, ~4 KB), freed on delete/error cleanup. Both RX loops now read into staging and `memcpy()` into the caller (PSRAM) buffer, eliminating the per-transaction bounce allocation that was the suspected failure source. TX payloads (≤250 B, already in the internal `buffer[]`) were never the problem and are unchanged.

**3. Errno + DMA-heap diagnostics at all 9 SPI transmit-failure sites** — new `SPI_XMIT_GOTO_ON_ERROR(ret, err)` macro replaces the 9 identical `ESP_GOTO_ON_ERROR(...)` sites (write ×2, read ×4, available ×2, flush ×1). Each failure now logs the real `esp_err_to_name(ret)` plus `heap_caps_get_free_size(MALLOC_CAP_DMA)` and the largest free DMA block, so the next wedge arrives with evidence instead of silence.

**4. Automatic recovery after 3 consecutive snapshot invoke failures (`eyes.c`)** — a streak counter lives in `snap_grab_frame_()`, shared by both snapshot paths (HTTP `snap` and `snaptest`):
- Invoke failure or image-timeout increments the streak; a successful capture resets it to 0.
- At streak == 3, `eyes_recover_camera(false)` runs: RST pulse via `sscma_client_reset()`, 1 s settle, up to 4 `set_model(1)` re-handshake attempts 300 ms apart, then sensor mode restored to `SENSOR_OPT_DEFAULT` (640×480). It runs inside the snap worker that owns the snapshot slot, so it cannot fight an active snapshot. The streak resets after the attempt (failed recovery retries after 3 more failures — no tight loop on a truly dead camera).

**5. Serial-only `eyes_reset` command (`link.c`)** — full manual recovery tool:

```json
{"t":"eyes_reset"}
{"t":"eyes_reset","rail":0}
```

- Refused over MQTT (`"serial console only"`), refused while a snapshot is in flight (`"snapshot in progress"`).
- No firmware OTA/flash-transfer state exists to refuse on: flashing is page-driven via esptool-js (the device resets into the ROM bootloader), so the firmware never sees a transfer — documented here rather than faked as an interlock.
- Sequence: rail low ~300 ms → rail high → 100 ms settle → `sscma_client_reset()` → 1 s wait → model re-handshake → sensor mode restore → normal `_mid`-correlated `ok`/`err` reply. `"rail":0` skips the power-cycle (warm RST only).
- Himax rail pin verified against the Seeed schematic: PCA9535 P13 = `EXP_Himax_EN`, HIGH = on, bitmask `1u << 11` (`PIN_HIMAX_RAIL`).

**New public API (`eyes.h`):** `eyes_recover_camera(bool cycle_rail)`, `eyes_snap_busy(void)`.

**Version:** `FW_VERSION` 0.4.1 → 0.4.2 in `main/main.c`.

## Known caveats / follow-ups

- The transient SPI errno that wedged 0.4.0/0.4.1 was never captured (old logs omitted it). If it recurs on 0.4.2, the new diagnostic line will name it; the staging buffer is expected to have removed the `ESP_ERR_NO_MEM` bounce-allocation path entirely.
- Auto-recovery takes ~2–4 s inside the failing snapshot's own worker (sync commands budget 15 s); the failing snapshot still returns an error, the *next* one benefits.
- Build environment note: `/tmp` (512 M tmpfs) is 100% full from a stale `/tmp/fwold/watcher-input-assistant/vendor` copy (2026-09-24, root-owned — left untouched). Builds and host tests were run with `TMPDIR=$HOME/workspace/.tmp-build-tmp` to dodge it. Someone should clean `/tmp/fwold`.
