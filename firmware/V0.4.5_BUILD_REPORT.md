## Telemetry triage — issues found

### 1. Spontaneous reboots (CRITICAL, root cause NOT proven)

**Evidence from telemetry.log (2026-09-27 01:49–01:52, fw 0.4.4):**
- "up" messages at 01:49:37, 01:49:46, 01:49:56, 01:50:36, 01:51:17, 01:51:27, 01:51:37, 01:52:07
- Intervals: 9s, 10s, 40s, 41s, 10s, 10s, 30s — **irregular**
- No panic, assert, Guru Meditation, or stack traces (silent resets)
- No `rst:` reset-reason lines forwarded for these boots (page telemetry gap)

**What the 0.4.4 report got wrong:**
The 0.4.4 report claimed the 0.4.3 loop was caused by the 9s bootloader RTC
WDT, citing `rst:0x3 (RTC_SW_SYS_RST)`. This is incorrect:
- `rst:0x3` = **software reset** (`esp_restart()`), NOT a watchdog. A RTC WDT
  reset shows as `rst:0x9` (RTCWDT_SYS_RST).
- The `rst:0x3` lines at 01:29 were during the failed 0.4.3 flash
  (invalid segment length), not the reboot loop.
- No `rst:` lines exist in telemetry for the 0.4.3/0.4.4 reboot loops.
- The 0.4.4 WDT-disable fix did not stop the reboots, and the intervals are
  irregular (not the metronomic 9s a WDT would produce).

**Hypotheses ranked by evidence:**
1. **Task WDT (5s, silent reset)** — `CONFIG_ESP_TASK_WDT_EN=y` with
   `CONFIG_ESP_TASK_WDT_PANIC` unset means a stuck task resets silently.
   But the observed intervals (9–41s) don't match a 5s WDT cleanly.
2. **Heap corruption / wild pointer** — irregular intervals suggest a crash
   bug, not a periodic WDT. The 0.4.3→0.4.4 delta includes the new LED
   queue code; 0.4.2 (stable) predates whatever 0.4.3 changed.
3. **Interrupt WDT (300ms)** — would fire much faster than observed; unlikely.
4. **Brownout** — no `rst:0xD` evidence; unlikely.

**Fixes in 0.4.5 (diagnostic + hardening):**
- `CONFIG_ESP_TASK_WDT_PANIC=y` in `sdkconfig.defaults` — the next reboot
  will print a panic with the stuck task name + backtrace instead of
  resetting silently. This is the key diagnostic.
- `main.c` now logs `esp_reset_reason()` at boot (`"reset reason: %d"`).
  Telemetry will capture WHY the device booted even though the page does
  not forward the ROM `rst:` line.

### 2. LED boot queue drops the BT green on every boot

**Evidence:** Every 0.4.4 boot logged `"boot complete, 1 queued transient(s)
dropped"`. The BLE-connected green flash was enqueued during boot but
`led_boot_complete()` drained the queue before the 50ms tick could play it.
The green never displayed.

**Root cause:** `led_boot_complete()` (called at ~3.5s, the "up" message)
emptied the FIFO while the 3s rainbow was still playing or the green was
still queued. The 0.4.4 design dropped leftovers; the timing made the drop
hit every boot.

**Fix (`components/led/led.c`):**
- `led_boot_complete()` now only clears `boot_queueing_` (new transients
  preempt again). It does NOT drain the queue.
- The 50ms tick pump condition changed from
  `if (boot_queueing_ && transient_ == TR_NONE ...)` to
  `if (transient_ == TR_NONE ...)` so it drains leftovers after boot.
  New transients never enter the queue post-boot (they preempt via
  `start_transient_locked()`), so the pump only drains boot leftovers.
- Log line changed to `"boot complete, queue draining (%d pending)"`.

**John's "crazy light shows":** most likely the 3s boot rainbow replaying on
every spontaneous reboot (every 9–40s), not an LED logic bug. The queue
mechanics themselves are sound (static FIFO, no heap, stuck-transient
watchdog intact).

### 3. SPD2010 touch controller I2C failures (known hardware issue)

**Evidence:** Every boot logs 3 ERROR lines:
- `SPD2010: read_tp_status_length(298): Tx failed`
- `SPD2010: tp_read_data(438): Read status length failed`
- `SPD2010: read_data(160): read data failed`

The touch controller does not ACK on I2C. This is the known touch
bring-up issue, not related to the reboot loop. No firmware change in
0.4.5 (John is aware; hardware investigation pending).
