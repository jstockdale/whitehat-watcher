## Why 0.4.9

Firmware 0.4.8 fixed the `nvs_task` PSRAM stack (static `DRAM_ATTR` via
`xTaskCreateStatic`) and booted cleanly through the early NVS panic. But
0.4.8 still boot-looped with a **different** assert, caught on John's
console over serial:

```
assert failed: xTaskGetHandle tasks.c:2855 (strlen( pcNameToQuery ) < 16)
```

Root cause: the stack high-water report in `components/link/link.c`
(`hwm_tasks[]`) looked up two sscma_client tasks by their full 20-char
creation names — `"sscma_client_process"` and `"sscma_client_monitor"`.
`xTaskGetHandle()` asserts `strlen < configMAX_TASK_NAME_LEN` (16), so
the lookup panicked right after `led: boot complete`, before any other
task could report. (FreeRTOS truncates stored names to 15 chars, so
even a non-asserting lookup with the full name would never match.)

John's call: don't paper over it with truncated lookup names — **rename
the tasks properly**.

## Changes

### 1. sscma_client tasks renamed (John's names)

**Before (`components/sscma_client/src/sscma_client_ops.c`):**
- `sscma_client_process` (20 chars) — the SPI/UART RX pump: polls Himax,
  reads bytes, parses AT frames
- `sscma_client_monitor` (20 chars) — the event dispatcher: waits on the
  reply queue, routes to callbacks

**After:**
- `sscma_client_process` → **`sscma_client`** (12 chars)
- `sscma_client_monitor` → **`sscma_monitor`** (13 chars)

All 8 task-creation sites updated (4 per task: `xTaskCreateStatic`,
`xTaskCreateStaticPinnedToCore`, `xTaskCreate`, `xTaskCreatePinnedToCore`
— both the function pointer and the name string literal). Both task
functions are file-local `static`s; no external references existed.

**`components/link/link.c`:** `hwm_tasks[]` now uses `"sscma_client"`
and `"sscma_monitor"` directly — no truncation games.

**Impact:** Fixes the v0.4.8 boot panic. Both names fit FreeRTOS's
15-char limit with headroom.

### 2. audit_psram_flash.py: task-name length checks

**New `check_task_get_handle_names()`:** fails the build if any string
passed to `xTaskGetHandle()` (direct literal or via a brace-initialized
string array) is ≥ 16 chars. Negative-tested against the v0.4.8
`hwm_tasks[]` (correctly flags both 20-char names); positive-tested
against the fixed `link.c` (clean).

**New `check_task_create_names()`:** fails the build if any
`xTaskCreate*` call (all four variants — the name is always the 2nd
argument) uses a name ≥ 16 chars. A creation name longer than 15 chars
silently diverges from the stored (truncated) name and breaks every
`xTaskGetHandle` lookup for it. Negative-tested against the old
20-char creation sites; positive-tested against the renamed
`sscma_client_ops.c`.

**Impact:** Both the v0.4.8 failure mode (long lookup name) and its
root enabler (long creation name) are now build failures, not
boot-time panics.

### 3. WIA1 host-test stub

`components/seal/test/host_stubs/esp_err.h` (new): minimal host stub
(`typedef int esp_err_t`, `ESP_OK`/`ESP_FAIL`) so `test_wia1.c` builds
on host without ESP-IDF headers. `wia1.c` already documented this
expectation ("esp_err.h comes from test/host_stubs"). Test-only; not
compiled into firmware.
