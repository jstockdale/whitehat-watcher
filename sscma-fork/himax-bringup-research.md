## 1. The Chip: Himax HX6538 (WiseEye2)

**[CONFIRMED]** — Source: `vendor/oshw-watcher/Hardware/HX6538_datasheet.pdf` (Himax DOC No. HX6538-A-DS, Preliminary v01, July 2023):

- **CPUs:** Dual ARM Cortex-M55 (Helium vector + FPU + TrustZone)
  - Big core: up to 400 MHz, 16 KB I-cache, 16 KB D-cache, 256 KB ITCM, 256 KB DTCM
  - Little core: up to 150 MHz, 16 KB I-cache, 16 KB D-cache
- **NPU:** ARM Ethos-U55 microNPU r2p0, up to 400 MHz, 64 MACs/cycle
- **SRAM:** 2.5 MB internal ultra-low-leakage SRAM (configurable system memory up to 2432 KB)
- **Boot ROM:** 64 KB internal boot ROM
- **Flash:** External 1–16 MB QSPI Flash, up to 100 MHz, **Execute-In-Place (XIP)** supported
- **Security:** CryptoCell-312, PUF (hardware root of trust + TRNG), TrustZone, secure boot, secure OTA
- **Power:** Multi-layer PMU (1st layer: always-on motion detection / image pre-processing; 2nd layer: M55+U55, normally power-gated), DVFS 0.8/0.9 V
- **Packages:** LQFP128, WLCSP65 (2.3×5.6 mm — used on Watcher per image-gen config `project_case1_blp_wlcsp.json`), QFN88
- **Debug:** SWD with SRSTN
- **Boot option pins:** `BOOT_OPT0/1/2` (AON domain, pulled low at reset per datasheet pin table)

### Boot chain (from image-gen partition layout) — **CORRECTED**

**[CONFIRMED]** — Source: `we2_image_gen_local/output_case1_sec_wlcsp/layout.json` (generated by Himax's `we2_local_image_gen`), cross-checked with the official image-gen guide:

| Flash offset | Size | Partition |
|---|---|---|
| 0x0 | 0x1000 (4 KB) | `hx_memory_descriptor` |
| 0x1000 | 0x13000 (76 KB) | `2nd_bootloader` (exec @ 0x3401F000) |
| 0x14000 | 0x14000 (80 KB) | `bootloader` (exec @ 0x34005000) |
| 0x28000 | 0x1000 (4 KB) | `hx_memory_descriptor_ota` |
| 0x29000 | 0x72000 (456 KB) | `cm55m_s_application` (our SSCMA firmware) |
| 0x9B000 | 0x2000 (8 KB) | `cm55m_s_application` (cont.) |

Boot sequence (inference from layout + guide): **64 KB mask ROM → reads memory descriptor @ 0x0 → verifies RSA signatures → 1st bootloader → 2nd bootloader → CM55 application.**

### The `ckBS` magic — **CORRECTED**

**[SDK-CONFIRMED]:** `ckBS` (`63 6b 42 53`) is the **signed-section magic of Himax's BLP (CRC+RSA) image format**, present at the start of every BLP-signed section (memory descriptor at `output.img` offset 0, each `sign_formal_*.bin` intermediate). The header continues `00 00 01 00 52 00 00 00 …` then a 32-byte hash field and RSA signature block. **It is NOT an SSCMA-specific marker** (earlier working assumption corrected). No public source documents what the letters stand for. (No web source documents the literal `ckBS` magic at all; confirmed by inspecting official SDK-generated images.)

### Image formats and secure boot

**[SDK-CONFIRMED]** — from the official image-gen user guide (`we2_image_gen_local/doc/WE2_CM_ImageGen_UerGuide.pptx`, Himax 2023.03):

- **Formats:** `RAW` (CRC only), `BLP` (CRC + RSA signature), `BLW` (CRC + signature + encrypt), `BLW_REENC` (CRC + signature + re-encrypt). A partition = a block signed by one RSA signature; sections carry .CODE/.DATA/.RODATA attributes.
- **Build cases:** Case 1 = one core secure-only; Case 2 = one core S/NS TrustZone; Case 3 = dual core secure-only; Case 4 = dual core S/NS. **The Watcher/SSCMA firmware is Case 1 BLP** (one secure CM55 core).
- **Secure boot [Himax-confirmed at high level; details not public]:** PUF root-of-trust + TRNG, CryptoCell-312, TrustZone, "secure boot, secure OTA", certificated secure debug (datasheet). The image-gen tree includes `key_gen_tool/` (RSA-2048/3072 key generation), OTP key burning via the "WE2 ISP Tool", and a cert chain in `secureboot_tool/cert/` (`ICVSBKey1.crt`, `OEMSBKey1.crt` — Himax as IC vendor vs. Seeed as OEM). **Not public:** hash algorithms, key hierarchy, fuse provisioning, rollback policy, whether sample keys are dev-only, the exact ROM verification flow. Do not infer production-grade security from the presence of sample certificates.

### Watcher board specifics

**[CONFIRMED]** — Source: `vendor/oshw-watcher/Hardware/SenseCAP_Watcher_v1.0_SCH.pdf` (extracted text):

- `BOOTOPT0` (WLCSP65 ball H1) → test point **TP10**, pulled to GND via **R63 100K**. (BOOT_OPT1/2 not found in extracted text — **[UNKNOWN]** strapping.)
- `TEST_MODE` → tied to GND.
- `HIMAX_RST` (RESETN) → test point **TP7**, pulled up to HIMAX_3V3 via R78 10K. Also driven by S3 via PCA9535 expander pin 7 (`PIN_SSCMA_RST`).
- **QSPI flash chip** (U16) connected to WE2 QSPI_DIO0–3 / QSPI_CS / QSPI_CLK. Part number not legible in extracted schematic text — **[UNKNOWN]**, but `flash_max_size: 0x1000000` (16 MB) in image-gen config.
- **S3 ↔ WE2 link is SPI**, not UART: `ESP_GPIO21/Himax_SPI_CS` (S3 GPIO21), SYNC = expander pin 6, RST = expander pin 7, 12 MHz, SPI mode 0. (Source: `firmware/components/eyes/eyes.c` header comment.)
- WE2 UART1 (PB6/PB7) pins are **shared with QSPI_CS/QSPI_CLK** in the pin-mux table — however, community evidence (see §4) confirms the Watcher **does** expose a Himax USB serial port to the PC. The exact on-board routing (likely a dual-UART USB bridge) was not traced pin-by-pin in this research. **Correction:** UART xmodem flashing IS accessible via USB; no physical rework needed.

## 3. How SSCMA Firmware Gets Flashed

### 3a. Grove Vision AI V2 (dev board) — UART xmodem

**[CONFIRMED]** — Source: `sscma-example-we2-main/README.md`:

1. Connect via USB-UART (micro-USB on EVB). Serial: **921600 baud**, 8N1, no flow control.
2. Hold any key (not Enter) + press **reset** → boot menu appears.
3. Press **`1`** → WE2 enters xmodem receive mode.
4. Send `output.img` via xmodem (TeraTerm/minicom, or `python3 xmodem/xmodem_send.py --port=/dev/ttyACM0 --baudrate=921600 --protocol=xmodem --file=output.img`).
5. Press `y` when prompted to reboot.

Alternative: `himax-flash-tool -d WiseEye2 -f <img>` (Edge Impulse CLI).

### 3b. SenseCAP Watcher — SPI OTA from the ESP32-S3

**[CONFIRMED]** — Source: `vendor/watcher-firmware/components/sscma_client/`:

The Watcher does **not** use UART xmodem. The S3 flashes the WE2 over the existing SPI bus using a dedicated OTA protocol:

- `sscma_client_flasher.h` exposes `sscma_client_new_flasher_we2_spi()` (and a UART variant, but the UART code path is **commented out** in the Watcher BSP).
- `bsp_sscma_flasher_init()` in `sensecap-watcher.c` creates the SPI flasher using the existing SSCMA client SPI handle, with reset via the IO expander (`BSP_SSCMA_CLIENT_RST_USE_EXPANDER`).
- Protocol (`sscma_client_flasher_we2_spi.c`, 595 lines):
  - `OTA_CMD_WRITE (0xF2)` / `OTA_CMD_READ (0xF3)` SPI commands
  - Enables WE2 ISP mode via register writes (`OTA_ENABLE_REG 0xD8`, `REG_D8_ISP_EN | REG_D8_TEST_MODE | REG_D8_SPI_DO_EN`)
  - Writes 256-byte chunks to `OTA_BASE_ADDR (0x38000000) + offset`
  - `OTA_START_OFFSET = 0x400000` (4 MB) — the OTA slot
  - CRC verification (`OTA_CRC_WRITTEN_ADDR`, `OTA_CRC_READ_ADDR`)
  - If `offset == 0`, clears the 4 KB "boot slot magic" at top of flash (`0x38000000 + 0x1000000 - 0x1000`), forcing boot from slot 0
- Our firmware already includes this flasher code (`firmware/components/sscma_client/` was forked from the vendor repo).

**[INFERRED]**: The 2nd bootloader checks the magic at top-of-flash to select boot slot. Writing the new image to the OTA slot (4 MB) and updating the magic = safe A/B-style update; the original slot stays intact until the new one is verified.

## 4. Community Experiences

### Bricking reports

**[CONFIRMED]** — No confirmed reports of a permanently bricked WE2 chip exist in public sources (Seeed forum, GitHub, Reddit — a site:reddit.com search returned nothing).

Grove Vision AI V2 (early 2024) had a **bootloader corruption** issue: devices stopped being detected by Windows/SenseCraft after firmware operations. Seeed acknowledged it ("We have now updated the latest Bootloader and have provided a detailed tutorial for flashing the firmware") and users recovered via the updated bootloader tutorial. (https://forum.seeedstudio.com/t/grove-vision-ai-v2-not-being-detected-by-windows-or-sensecraft/276045)

One user (MatBax) with a corrupted bootloader **fixed it** with Seeed's recovery procedure, but noted that manual xmodem flashing never worked reliably for him even before — the UART boot-menu entry is finicky on the V2. (https://forum.seeedstudio.com/t/sensecraft-ai-web-toolkit-not-working/275936)

**No "bricked my Watcher's Himax" threads found.** The closest from-source-build issue is sensecap-watcher-firmware #69: a developer built the ESP32 `factory_firmware` from public source and got a non-functional SPI handshake (`sscma_client_get_info` "request id failed") while the prebuilt binary worked — a silent source-vs-factory divergence, but on the ESP32 side (trivially re-flashable), not the WE2. (https://github.com/seeed-studio/sensecap-watcher-firmware/issues/69)

### Custom WE2 firmware on the Watcher — yes, it's been done

**[CONFIRMED]** — Multiple community sources:

- **suharvest/sscma-example-we2** documents building `EPII_CM55M_APP_S` with `TARGET=SENSECAP_WATCHER` (without it, "will fail with memory overflow errors"), generating `output.img` via `we2_local_image_gen`, and flashing to the Watcher. **Critical detail:** the ESP32 firmware can interfere with Himax flashing — their `flash_himax_safe.py` holds the ESP32 in reset via DTR/RTS during the flash. Port layout on macOS: Himax = `/dev/cu.usbmodem…51` (lower-numbered), ESP32 = `/dev/cu.wchusbserial…53`. (https://github.com/suharvest/sscma-example-we2/blob/HEAD/CLAUDE.md)
- **orulink-ai/watcherobot_python_sdk** describes a `ptl` backend = custom JPEG-transport firmware for the Watcher's WE2 — third parties build and run non-stock firmware on the Watcher's Himax. (https://github.com/orulink-ai/watcherobot_python_sdk/blob/HEAD/docs/vision-diagnostics.md)
- **sensecraft-solutions** documents the Watcher xmodem flash sequence and per-model flash address map (base FW @ 0x000000; model slots @ 0x400000/0x510000/0x600000/0x700000). Warns: "Do NOT disconnect during flashing." (https://github.com/suharvest/sensecraft-solutions/blob/HEAD/skills/prepare-himax-firmware/SKILL.md)

### Seeed's official stance

**[CONFIRMED]** — "We do not recommend that any user make any kind of modifications to the Himax firmware. The methods we provide are limited to use for restoring the firmware in special cases." (https://github.com/Seeed-Studio/OSHW-SenseCAP-Watcher, README "For Himax Firmware")

Official restore: `pip3 install python-sscma` then `sscma.cli flasher -f firmware.img` on the Himax serial port. The OSHW repo hosts the factory Himax image + HX6538 datasheet + full schematic. The OSHW README confirms the Watcher shows **two serial ports**: "If you find that there is no progress when flashing, then the wrong flash serial port may be selected and you may need to switch to another one."

### Flashing pitfalls (community-confirmed)

- **Wrong serial port:** The #1 gotcha. On Windows pick the COM port with **SERIAL-A** (Himax); SERIAL-B = ESP32. On macOS/Linux, the lower-numbered port (`ttyACM0`).
- **ESP32 interference:** Hold the ESP32 in reset (DTR/RTS) during Himax flashing.
- **Flash hangs:** "if the flashing process hangs, just cancel it (Ctrl+C) and start once again." (Edge Impulse / himax-flash-tool README)
- **Boot-menu entry unreliable:** Hold any key (not Enter) + press reset, then press `1`. May take multiple tries.
- **USB-serial driver:** One "un-flashable" case was fixed by updating the CH343 driver via Windows Device Manager — not a brick at all. (https://forum.seeedstudio.com/t/grove-vision-ai-2-can-t-deploy-models-using-sensecraft-seeed-cc/279624)
- **I2C bootloader recovery** (`we2_iic_bootloader_recover` in Seeed_Arduino_SSCMA): works from ESP32-class boards only, may need 3–10 attempts, ~10 sec when it works. (https://github.com/seeed-studio/seeed_arduino_sscma/blob/HEAD/examples/we2_iic_bootloader_recover/README.md)

### No remote/AT-based WE2 firmware update exists

**[CONFIRMED]** — The SSCMA AT protocol spec (`SSCMA-Micro/docs/protocol/at-protocol-en_US.md`, v2025.02.11) contains **no** `AT+UPDATE` or firmware-update command. Firmware updates go via USB + browser xmodem (SenseCraft web toolkit) or `sscma.cli flasher`. The WE2 has no network interface of its own — any remote update would need ESP32 proxying, and no public project does this.

## 5. Recovery

### Recovery methods (community-verified)

1. **UART xmodem reflash via boot menu** — hold any key (not Enter) + press reset → press `1` → xmodem send image → `y` to reboot. Works regardless of app-firmware state (the menu comes from the bootloader, not the app). On the Watcher: use the **Himax serial port** (SERIAL-A / lower-numbered), hold ESP32 in reset via DTR/RTS.
2. **Factory image restore** — flash the factory `.img` over the same xmodem path. For Grove V2: `Seeed_SenseCraft_AI_2023_12_19T183401_402.img` (in our local repo). For Watcher: factory image is in the OSHW repo (`Seeed-Studio/OSHW-SenseCAP-Watcher/Hardware/`).
3. **I2C bootloader recovery** — `we2_iic_bootloader_recover` Arduino sketch from an ESP32-class board. May need 3–10 attempts.
4. **SPI ISP via S3** — the S3's SPI flasher (§3b) writes directly to WE2 hardware registers. **[INFERRED]** This bypasses the WE2's firmware entirely (hardware test-mode path), making it the most robust recovery method — but it is **not** community-verified for recovery; the vendor code is written for the OTA update flow.
5. **Seeed's updated bootloader** — if the bootloader itself is corrupted, Seeed's early-2024 tutorial + updated bootloader image fixed the Grove V2 cases.

### What we know about the boot ROM

- **64 KB mask ROM** **[CONFIRMED]** (datasheet) — cannot be erased.
- **ROM download protocol** — **[UNKNOWN]**: the datasheet does not document BOOT_OPT pin meanings or any ROM-based download mode. The xmodem menu appears to come from the **flash bootloader**, not the ROM.
- **Implication:** If the flash bootloader (0x1000–0x28000) is corrupted, UART xmodem recovery may fail. The SPI ISP path (§3b) would then be the fallback. **We must never write to the bootloader partitions** — only the application partition (0x29000+) and OTA slot.

### Physical recovery access

- **TP7** = HIMAX_RST (reset), **TP10** = BOOTOPT0 (100K pulldown to GND). **[CONFIRMED]** from schematic.
- **Bottom RST button** on the Watcher case (user guide). **[CONFIRMED]** from community docs.
- BOOT_OPT1/2 strapping: **[UNKNOWN]** (not found in schematic text extraction).

## 6. Factory Image Backup

**Watcher's factory WE2 firmware:** available in the OSHW repo (`Seeed-Studio/OSHW-SenseCAP-Watcher/Hardware/`). **[CONFIRMED]** from OSHW README. We should download and archive it with SHA-256 before any flash.

**Backup procedure (before any flash):**

1. `AT+VER` → record factory firmware version string.
2. **Readback attempt:** Use the S3's SPI flasher `OTA_CMD_READ (0xF3)` path to dump the application partition (0x29000, ~464 KB) and the partition table (0x0, 4 KB). Verify `ckBS` magic in the dump. Store with SHA-256.
   - If readback works: we have a byte-exact backup.
   - If readback fails: fall back to the OSHW factory image + slot-0 preservation strategy below.
3. **Slot strategy:** Flash only the OTA slot (4 MB offset) or the application partition, **never** the bootloader partitions (0x0–0x28000). The factory image in slot 0 stays intact; the boot magic can be reverted to roll back.

## 7. OV5647 Sensor Modes

### Datasheet specs

**[CONFIRMED]** — OV5647 preliminary datasheet v1.0 (Nov 2009):

- **Image array:** 2624×1956 physical; 2592×1944 active/output. 1.4 µm pixels, 1/4" optical format.
- **Output:** 8/10-bit RAW Bayer. 2-lane MIPI CSI-2 (+ DVP parallel).
- **Datasheet mode table:**

| Output | FPS | Method | Pixel clock |
|---|---|---|---|
| 2592×1944 | 15 | full | 80 MHz |
| 1920×1080 | 30 | crop | 68 MHz |
| 1280×960 | 45 | crop+bin | 91.2 MHz |
| **1280×720** | **60** | **crop+bin** | **92 MHz** |
| 640×480 | 90 | crop+bin | 46.5 MHz |
| 320×240 | 120 | crop+bin | 32.5 MHz |

### Is 1280×720 native?

**[CONFIRMED]:** 1280×720 is a **datasheet-listed sensor output mode** (60 fps, crop + 2×2 binning of a 16:9 window). But **no public driver ships its register table** — not upstream Linux (`drivers/media/i2c/ov5647.c`: only 2592×1944, 1920×1080, 1296×972, 640×480), not raspiraw, not the Himax/Seeed example.

**[INFERRED] register recipe** (from web research, clearly untested — needs hardware validation):

The three public 2×2-binned modes all show output = window/2 minus a 16-col / 6-row margin. For exact 1280×720, the window must be (1280+16)×2 × (720+6)×2 = **2592×1452**:

| Register | Value | Meaning |
|---|---|---|
| `0x3800/0x3801` | `0x00, 0x00` | X start = 0 |
| `0x3802/0x3803` | `0x00, 0xFC` | Y start = 252 (centers 1452 rows) |
| `0x3804/0x3805` | `0x0A, 0x1F` | X end = 2591 |
| `0x3806/0x3807` | `0x06, 0xA7` | Y end = 1703 (1452 rows) |
| `0x3808/0x3809` | `0x05, 0x00` | X output = 1280 |
| `0x380A/0x380B` | `0x02, 0xD0` | Y output = 720 |
| `0x3814/0x3815` | `0x31` | 2×2 binning X/Y increment |
| `0x3820` | `0x41` | vertical binning enable |
| `0x3821` | `0x03` or `0x07` | horizontal binning enable (bits 1–2 differ between sources — copy from base table) |
| `0x380C/0x380D` | `0x07, 0x68` | HTS = 1896 |
| `0x380E/0x380F` | computed | VTS = pixel_clk / (HTS × fps); ~809 (`0x03,0x29`) for 60 fps @ 92 MHz |
| PLL regs | copy from working binned table | `0x3036`=`0x69`, `0x3612`=`0x59`, `0x3618`=`0x00` |

### What the Pi did

**[CONFIRMED]:** The Raspberry Pi Camera v1 never had the sensor emit 1280×720. Its "720p" was **1296×730 on-sensor** (2×2-binned 16:9 crop, up to 49 fps) + **GPU downscale** to 1280×720. Exact Pi registers are in raspiraw's `ov5647_modes.h` (mode5). On the WE2 there is no GPU — 720p must come from the sensor natively.

### Himax/Seeed OV5647 integration

**[CONFIRMED]:** The Seeed WE2 example (`tflm_yolov8_od`) has only **two** register tables:
- `OV5647_mipi_2lane_640x480.i` (binned)
- `OV5647_mipi_2lane_2592x1944.i` (full-res)

Driver file is `cisdp_sensor.c` (not `drv_ov5647.c` — that filename was not found anywhere public). Config: 2 CSI lanes, RAW10, 440 Mbit/s per lane. **No 720p table exists.**

### WE2 datapath gotchas for 720p

**[CONFIRMED]** from `cisdp_cfg.h` / `cisdp_sensor.c`:

- **Pipeline order:** SENSOR → INP_CROP → INP_BINNING → INP_SUBSAMPLE. INP cannot upscale or arbitrary-resize — only ÷2/÷4/÷8 binning and ÷2/÷4 subsample. **720p must come from the sensor** (§7 recipe above); INP crop stays disabled for a native 16:9 stream.
- **HW5x5:** accepts 1280×720 (min 8×8, width÷8, height÷4 — 1280/8=160, 720/4=180 ✓). Can center-crop to model size (e.g., 640×640). Keep crop starts even for Bayer phase.
- **JPEG engine: max 640×640** (min 16×16, dims ÷16). Full-frame 720p JPEG is **impossible** through HW5x5→JPEG. 720p capture must use the WDMA3 RAW/RGB path, or a ≤640×640 cropped JPEG.
- **MIPI headroom:** 1280×720 RAW10 @ 60 fps = 553 Mbit/s; link provides 880 Mbit/s. Fine.
- **SRAM budget [INFERRED — must verify]:** example sizes WDMA3 for 640×480×3 (921 KB). A 1280×720 RGB frame is 2.76 MB. Check against SRAM0+SRAM1 before enabling. YUV400 (922 KB) or YUV420 (1.38 MB) at 720p are safer first targets.
- **CSI RX timing:** `set_mipi_csirx_enable()` computes FIFO fill from `OV5647_SENSOR_WIDTH/HEIGHT` defines — must update to 1280/720 with the new table.

### Phase 2 implementation guidance

1. Add a `OV5647_mipi_2lane_1280x720.i` register table using the recipe above.
2. Wire it into `cisdp_sensor.c` mode selection (new `opt_id` or AT command).
3. Update `OV5647_SENSOR_WIDTH/HEIGHT` to 1280/720 for CSI timing.
4. Disable INP binning/subsampling for this mode (sensor already outputs 720p).
5. Verify WDMA3 SRAM sizing; start with YUV400/YUV420 if RGB doesn't fit.
6. Validate on hardware: check `AT+INVOKE` output dimensions, then snapshot path.

## Bring-Up Plan (Revised)

We have **two independent flashing paths** — this is excellent redundancy:

| Path | Method | Requirements | Risk |
|---|---|---|---|
| **A. USB-UART xmodem** | Himax serial port, 921600 baud, hold-key+reset → `1` → xmodem | Physical USB access, ESP32 held in reset | Low — standard flow, community-verified on Watcher |
| **B. S3 SPI OTA** | `sscma_client_new_flasher_we2_spi()` from our S3 firmware | S3 firmware with flasher integrated, MQTT delivery of image | Medium — code exists but we haven't exercised it |

### Recommended sequence

1. **Reconnaissance (no flash):** `AT+VER` → record factory FW version. Download OSHW factory image, archive with SHA-256.
2. **Backup:** Attempt QSPI readback via Path B (`OTA_CMD_READ`). Store dump + SHA-256.
3. **Path A dry run:** Flash `watcher_sscma_v0.1.img` (unmodified baseline) via USB-UART xmodem. If it boots and `AT+VER` responds, our build toolchain is validated end-to-end.
4. **Phase 1:** Flash `watcher_sscma_v0.2_roi.img` via Path A. Verify `AT+ROI?` works.
5. **Phase 2:** Implement 1280×720, flash via Path A.
6. **Path B (later):** Integrate the SPI flasher into our S3 firmware for remote/MQTT-driven WE2 updates. This is the long-term goal — no physical access needed.

### Safety rules

- **Never** write to bootloader partitions (0x0–0x28000).
- **Never** flash without the factory image archived locally.
- **Always** validate the baseline (v0.1) before flashing modified (v0.2+) images.
- John's explicit approval required before each flash (standing rule).
